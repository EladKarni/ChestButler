## 1. "What changed" for the consolidated 2.0.0 changelog

Raw material, not copy — each commit body has the full detail.

**Organize v2 (W1).** Organize now censuses every accessible chest in range, sizes each category by
volume, claims empty chests as new homes near the matching station, and packs everything in — one
press tidies the whole base instead of only moving items that already had a home. Categories spill
across as many chests as they need. Gear is filed into weapons/armor/tools. Small leftovers share a
`misc` chest. A chest labelled `sort: off` is now left entirely alone, both as a source and as a
target. Claimed homes persist, so a second press on a tidy base moves nothing. New config:
`MovesPerSecond` (replacing the framerate-dependent `MovesPerTick`), `MaxMovesPerRun`, `IncludeGear`,
`MiscPromoteSlots`, `ToolTokens`/`WeaponTokens`/`ArmorTokens`. The mod now measures its own cost and
throttles itself, so config is a ceiling rather than a tuning dial.

**Gather (W2).** A Gather button in the crafting panel, on every station, for Craft and Upgrade:
shows "(N stored)" beside each ingredient and pulls the shortfall for the shown craft amount out of
nearby chests into your inventory.

**Dedicated Sorter Chest (W3).** A craftable reinforced chest that is a Sorter out of the box —
workbench, 10 Wood + 5 BronzeNails, under Furniture.

**Gamepad (W4).** ChestButler's buttons are reachable with a controller's D-pad.

**Also worth a user-facing line** (from the 1.1.2 audit, now relevant because W1 makes it matter):
the sign syntax is still undocumented in the README. Roadmap §9c flags this as release-prep work —
`sort:`, group names, `pN`, and `off` now that `off` protects a personal stash.

## 2. Release mechanics (unchanged, restated so it is in one place)

- **2.0.0 is a MAJOR bump.** Under `VersionStrictness.Minor` a 1.1.x peer and a 2.0.0 peer refuse each
  other: server and every client update together.
- **The Sorter Chest is a custom prefab**, so it must exist on the server and all clients. This is the
  reason 2.0 cannot ship as a patch.
- **The `PATCH_ONLY` server updater will skip 2.0.0.** Deploy by hand, then set
  `.chestbutler_deployed` to `v2.0.0` so 2.0.x patches auto-flow again — the same bookkeeping as the
  1.0.2→1.1.0 crossover.
- Removing the mod after players build Sorter Chests orphans those pieces. Worth a line in the
  Thunderstore description.
- Version bump touches csproj + `Plugin.cs` `ModVersion` + `pkg/manifest.json` together —
  `build.sh` has a consistency guard.

## 4. Decisions I made that are yours to overrule

All config-driven, so none needs a rebuild. Fuller reasoning in each plan doc.

1. **Gear buckets are Organize-only, not `[ItemGroups]` groups** — so the live sorter tick still does
   not route gear; only Organize does. `[ItemGroups]` cannot express "all `ItemType.Tool`", which
   §16.4.4 notes itself.
2. **Pickaxes file as tools, axes stay weapons** — `[Organize] ToolTokens = "pickaxe*"`.
3. **`MiscPromoteSlots = 24`** — one vanilla chest's worth before an ungrouped type earns its own home.
4. **Sorter chests remain non-targets for Organize** — this closes the W1→W3 dependency by decision.
   Making them targets would have Organize fill a chest whose whole job is to empty itself: the same
   livelock class as §15.8. Reasoning in `docs/sorter-chest-plan.md` §4.
5. **The Sorter Chest inherits the vanilla reinforced-chest icon** — legible, but indistinguishable at
   a glance in the build menu. The `Assets/**` glob is ready if you want to draw one.

## 5. Deliberately not built

- **§16.2.8 / §15.9 multi-sorter claim stamp.** Two players organizing overlapping radii is a real
  race, but the stamp needs a claim-expiry policy and peer-identity scheme that is specified nowhere,
  and getting it wrong strands chests as permanently claimed. Wants its own design. The in-flight
  guard covers the single-client case.
- **True per-move completion counts.** `RemoveItemFromChest` returns a handle and W1 tracks
  outstanding requests through `PackageHandler`, but `RequestChestRemoveResponse.Success`/`.Amount`
  are consumed inside MUC and exposed nowhere. Reading them needs a Harmony patch on
  `InventoryHandler.RPC_RequestItemRemoveResponse` — patchable, but new coupling to MUC internals, so
  it is a decision rather than something to slip in. The HUD currently reports issued, could-not-move,
  no-room and timed-out separately, each labelled honestly.
- **Tidy mode** — deferred to 2.1 per the owner decision. No ZDO flag, no tick, no toggle.
- **A synced in-use flag** (handoff §7). W1 fixed the specified part — the destination is gated on ZDO
  ownership rather than the local-only `m_inUse` — but the networked flag itself is still undesigned.
- **README / Thunderstore copy and the sign-syntax documentation** — release-prep, yours.

## 6. Two file-ownership deviations, both flagged in their commits

1. **`Core/SorterBehaviour.cs`** (W1) — roadmap §3 says untouched in 2.0, but §16.6 names the sorter
   tick interval and the miss cooldown as two of the three self-throttle levers, and both live there.
   Four lines. A throttle that left the tick — which §16.3 calls "the path that actually breaks the
   game" — unthrottled would have satisfied the file list and built the wrong thing.
2. **`Core/ContainerTracker.cs`** (W2) — listed reads-only for W2, but every existing query is centred
   on a `Container` and excludes that Container from its own results, which is wrong for a
   player-centred search. Gained one append-only accessor, `AccessibleNear(Vector3, float)`, with
   `Candidates` re-expressed as a call into the same private core so the two cannot disagree.

## 7. The honest summary of test coverage

The offline suite covers what can be covered without a game: the allocator end-to-end (including the
§12 acceptance test at 5 and 400 chests, with a negative control proving `psort_home` is load-bearing),
Gather's shortfall arithmetic, the name matcher, the group-order invariant, and the bucket-key formats
that get persisted into ZDOs.

**Everything else is unverified, and none of it has run in a game.** In rough order of how much I would
want to see before release: the two-client dedicated-server session over a shared hall (which
§16.5 says exercises six of §16.2's eight findings on its own), the Sorter Chest's zone-reload
behaviour (test C in its plan — the `WasDefaulted` marker only matters across a reload), the whole of
Gather's UI and transfer path, and W4, where I have not seen a controller touch any of it and the
failure mode is "still not reachable" rather than anything worse.
