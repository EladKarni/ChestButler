# ChestButler 2.0 — open follow-ups from in-game testing

Raised during the first real play-test of the 2.0 build. None of these block the
allocator fix; they are decisions and polish the integrator owns.

## RESOLVED: incumbent adoption + marker fixed point (landed on dev)

The "my organized ore chest was emptied for no reason" complaint is fixed by two planner changes:
the **marker fixed point** (Plan iterates until its own psort_home output is consistent with its
input, so externally divergent live markers can no longer cause press-2 churn) and **incumbent
adoption** (an anchorless category adopts the chest it already mostly lives in, recorded once).
Verified: 179-assertion suite, 30/30 mutation kills, 3x300-seed fuzz (stale/live/incumbent modes)
all press-2-zero, clean-room reproduced independently.

**One designed exception, accepted:** if a category has outgrown its incumbent chest and a nearer
chest can hold ALL of it, it relocates once to where it fits (visible reason: it no longer fit).
Keeping the undersized chest as primary and spilling was considered and rejected for now — it
splits the category with no visual cue. Revisit only if players report it.

## DECISION (owner, 2026-08-10): station adjacency is FEED-IN PROCESSORS ONLY

Gather changed the workflow: stand at the station, Gather exactly what the recipe needs from
anywhere in range, craft, dump leftovers into a Sorter chest to be returned. Pooling materials
beside crafting stations no longer serves that loop — and workbench adjacency was the top source
of routing surprises all through 1.1.x. The default [Stations] map now maps only smelter, blast
furnace and fermenter (no recipe UI — you feed them by hand, so proximity pooling is still the
only workflow that serves them). Crafting stations were REMOVED from the defaults.

Mechanism unchanged: the Station anchor tier, StationRange and CustomStations all remain, so any
server can re-add e.g. '$piece_forge=metals,ores' via CustomStations. Migration note for release
prep: removing a bind makes stored per-station cfg lines inert, so upgraded servers lose
crafting-station attraction automatically — put that in the changelog, and rewrite the README /
Thunderstore station table (it currently headlines forge/cauldron attraction).

Test-script impact: expectations that route Bronze to a forge chest or DeerMeat to a cauldron
chest (W1-G1, W4-R1, drill 7) are obsolete as written — smelter/fermenter expectations stand.

## FINDING (staging, 2026-08-10): curated cross-bucket chests MUST be protected before Organize

The owner's hand-curated "health heavy foods" chest was dispersed by Organize and refilled as a
general meat/cooking home. Working as designed but a bad surprise: the allocator organizes by
ITEM-TYPE buckets, and a curated selection SPANNING buckets (a meals chest, a "going on a trip"
kit) is a player concept the census cannot see. Adoption does not protect it either - adoption is
per-bucket, and a chest holding a LITTLE of many types loses to the big homes.

The protection patterns (release-prep must document these LOUDLY, before-first-Organize):
- `sort: off` sign (or area-off): full protection; Pull still restocks it on click.
- Pin (Auto): the chest becomes THE home for those types - protected and auto-restocked, but it
  attracts all of that type in range; right for "the meals chest", wrong for "a sample of each".
- Manual does NOT protect contents from Organize (target-exclusion only; still a source).

2.1 candidate: a "keep" concept - protect quantities/curation without claiming the whole type.

## PROD SOAK PROTOCOL (first week of 2.0.0 on the live server)

- **Before the update:** full AMP world backup; keep the 1.1.2 DLL beside it. Config review
  against new defaults (the Radius=32 incident class): Radius, the ores line, new sections.
- **Rollback caveat, tell the group:** hold off placing Sorter Chests during the soak week.
  They are a custom prefab — rolling back to 1.1.2 orphans placed ones (the game removes
  unknown prefabs on load). Everything else survives a rollback (new ZDO keys are ignored).
- **Soft rule for the group:** one person presses Organize at a time. The two-player
  Organize race is the one path with no code-level arbitration (claim stamp deferred to 2.1
  by design, handoff §5) — its failure mode is churn, not loss, but do not invite it week 1.
- **Detection:** Debug logging ON (server + owner's client) for the week; owner skims or
  sends logs after sessions - look for "timed out", "skipped", repeated "[throttle]", and
  any "Organized N" where N disagrees with the preview. Players told: if items seem to
  vanish, say so IMMEDIATELY with the chest location (the log will show the move).
- **After a clean week:** Debug off, soak over, 2.1 planning starts.

## 1. Gather greys out immediately after a successful gather — decide the intent

**Observed.** With 0 wood carried and a x5 craft needing 40 wood, `Gather (40)` pulled the
40 wood, and the button then greyed out.

**Why.** `Gatherable = min(Shortfall, InStorage)` and `Shortfall = max(0, Needed - InPlayer)`
(`Core/GatherMath.cs`). Once the pull lands, the player carries the full requirement, the
shortfall is zero, and there is by definition nothing left to gather. The button is
reporting the truth.

**The open question** is what the button should mean once the requirement is met:

- **(a) Leave it.** Greyed = "you have what this recipe needs". Simplest, and already correct.
- **(b) Top up to a full stack.** Gather pulls up to `m_maxStackSize` rather than to the
  requirement, so a batch crafter ends up with a working stack instead of exactly enough.
  Changes `Needed`, so it changes the `(N)` annotation's meaning too.
- **(c) Re-arm per craft.** After crafting consumes the materials the shortfall reappears and
  the button lights up again on its own — this already happens; the greying is only for as
  long as the materials are actually in the inventory.

Owner has not chosen. No code change made.

## 2. The Sorter Chest sits at the END of the Furniture tab, not beside the other chests

**Observed.** The piece is buildable and works, but it is appended after every vanilla
Furniture entry rather than grouped with the vanilla chests, so it is hard to find.

**Why.** Jotunn's `PieceManager.AddPiece` appends to the Hammer's `PieceTable.m_pieces`;
registration order is the only order it has.

**Possible fix (not implemented).** After registration, locate the vanilla `piece_chest`
index in the Hammer `PieceTable.m_pieces` and move our entry to `index + 1`. Needs to run
after the vanilla table is populated and to be idempotent across world loads. Worth
confirming it survives Jotunn re-adding pieces on world change before shipping.

Cosmetic only. A distinct icon (currently inherited from the vanilla reinforced chest) is
the other half of the same discoverability problem — see `docs/sorter-chest-plan.md` §5.

## 3. The sorter-tick regression test needs a better shape

**Observed.** The proposed W4-R1 procedure (two signs reading `sort: ores` / `sort: hides`,
plus a forge chest and a cauldron chest, then five spawned stacks) was judged not the best
way to test the tick.

**Why it is awkward.** It sets up four routing tiers at once — sign group, station
adjacency, and the ores/scrap token fix — so a single wrong outcome does not identify which
tier broke, and sign placement is fiddly (the sign must be the nearest container's, under
1 m, and its chest must be the nearest one to it).

**Alternative worth considering:** test one tier per press with pins instead of signs —
pins are set from the chest UI with a button, need no placement, and are the same
`FilterSpec.Items` path a sign token feeds. Then station adjacency separately with a single
empty chest by the forge. Owner to decide the final shape.
