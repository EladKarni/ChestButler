## 1. Gather greys out immediately after a successful gather — decide the intent

**Observed.** With 0 wood carried and a x5 craft needing 40 wood, `Gather (40)` pulled the
40 wood, and the button then greyed out.

**Why.** `Gatherable = min(Shortfall, InStorage)` and `Shortfall = max(0, Needed - InPlayer)`
(`Core/GatherMath.cs`). Once the pull lands, the player carries the full requirement, the
shortfall is zero, and there is by definition nothing left to gather. The button is
reporting the truth.

**The open question** is what the button should mean once the requirement is met:

- **(a) Leave it.** Greyed = "you have what this recipe needs". Simplest, and already correct.
- **(b) Top up to a full stack.** Gather pulls up to `m_maxStackSize` rather than to the
  requirement, so a batch crafter ends up with a working stack instead of exactly enough.
  Changes `Needed`, so it changes the `(N)` annotation's meaning too.
- **(c) Re-arm per craft.** After crafting consumes the materials the shortfall reappears and
  the button lights up again on its own — this already happens; the greying is only for as
  long as the materials are actually in the inventory.

Owner has not chosen. No code change made.

## 2. The Sorter Chest sits at the END of the Furniture tab, not beside the other chests

**Observed.** The piece is buildable and works, but it is appended after every vanilla
Furniture entry rather than grouped with the vanilla chests, so it is hard to find.

**Why.** Jotunn's `PieceManager.AddPiece` appends to the Hammer's `PieceTable.m_pieces`;
registration order is the only order it has.

**Possible fix (not implemented).** After registration, locate the vanilla `piece_chest`
index in the Hammer `PieceTable.m_pieces` and move our entry to `index + 1`. Needs to run
after the vanilla table is populated and to be idempotent across world loads. Worth
confirming it survives Jotunn re-adding pieces on world change before shipping.

Cosmetic only. A distinct icon (currently inherited from the vanilla reinforced chest) is
the other half of the same discoverability problem — see `docs/sorter-chest-plan.md` §5.

## 3. The sorter-tick regression test needs a better shape

**Observed.** The proposed W4-R1 procedure (two signs reading `sort: ores` / `sort: hides`,
plus a forge chest and a cauldron chest, then five spawned stacks) was judged not the best
way to test the tick.

**Why it is awkward.** It sets up four routing tiers at once — sign group, station
adjacency, and the ores/scrap token fix — so a single wrong outcome does not identify which
tier broke, and sign placement is fiddly (the sign must be the nearest container's, under
1 m, and its chest must be the nearest one to it).

**Alternative worth considering:** test one tier per press with pins instead of signs —
pins are set from the chest UI with a button, need no placement, and are the same
`FilterSpec.Items` path a sign token feeds. Then station adjacency separately with a single
empty chest by the forge. Owner to decide the final shape.
