# Why Organize won't converge — a code walkthrough

*Written 2026-08-10, against commit `fa50c09` (build `634897f8`), from the staging session log
after the world reset. This is the document trail for the last open executor bug before 2.0.*

---

## 1. The 30-second map

One Organize press runs this pipeline:

```
press 1 ──► BuildPlan (preview)          "move 5838 items across 47 chests — press again"
press 2 ──► BuildPlan (rebuilt fresh) ──► Execute ──► Run coroutine
                                                        │  per move: TryIssue guard chain
                                                        │  ──► MUC RemoveItemFromChest request
                                                        │  ◄── response (some frames later)
                                                        └─► "Organized N items into M chests"
```

Two halves, deliberately separated:

- **The planner** (`OrganizePlanner.cs`) is pure math over snapshots. It never touches the world.
  Census → classify every item into one bucket → reserve chest *slots* per bucket from one ledger →
  emit moves, **evictions ordered before fills**.
- **The executor** (`Organizer.cs`, `Run` coroutine) replays those moves against the *live* world,
  re-validating each one, because the world may have changed since the snapshot. On a dedicated
  server it cannot just write inventories — chests are owned by other peers — so every transfer is a
  MultiUserChest (MUC) network request with a round-trip.

Everything below is about the seam between those halves, and the seam between the executor and MUC.

## 3. The planner half — how a plan gets built

### 3.1 Census and classification

`BuildPlan` snapshots every accessible chest into POD views. Each stack gets a *merge key* — same
item at different New Game+ world levels can never merge, so they are distinct piles
([Organizer.cs:159](../src/ChestButler/Core/Organizer.cs:159)):

```csharp
// Stacks that cannot merge get distinct identities (see sampleByKey above).
string key = it.m_worldLevel > 0 ? norm + "#" + it.m_worldLevel : norm;
```

Every item type resolves to exactly one bucket — pin → group → gear → per-type
([Organizer.cs:264](../src/ChestButler/Core/Organizer.cs:264), `ClassifyNorms`).

### 3.2 The slot ledger

The allocator budgets **slots, not items**. Demand per bucket is `ceil(total / maxStack)` summed
per merge key; supply per chest is
([OrganizePlanner.cs:546](../src/ChestButler/Core/OrganizePlanner.cs:546)):

```csharp
var slotsLeft = new int[chests.Count];
...
slotsLeft[i] = c == null || c.ExcludedAsTarget
    ? 0
    : Math.Max(0, c.TotalSlots - immovableSlots[i]);
```

Note what this assumes: **every stack the plan intends to move OUT of a chest frees its slot.**
The planner counts a full chest as having room, *provided its current contents are being evicted
elsewhere in the same plan*. That assumption is made safe at execution time by ordering
([OrganizePlanner.cs:605](../src/ChestButler/Core/OrganizePlanner.cs:605)):

```csharp
// ---- 7. evict before fill ------------------------------------------------------------
OrderEvictionsFirst(moves);
```

Hold that thought: **if an eviction silently fails, every fill behind it inherits a full chest** —
and reports `NoRoom` even though the planner (correctly, by its own model) said `0 items with no
room`. This is the bridge between Anomaly B and Anomaly C: *they are probably one bug, not two.*

## 4. The executor half — how a move gets issued

### 4.1 The guard chain

Every move is re-validated live, immediately before issuing
([Organizer.cs:678](../src/ChestButler/Core/Organizer.cs:678), `TryIssue`). Abridged to the guards
that fired in your log:

```csharp
// stack gone since the plan was built
if (!sInv.GetAllItems().Contains(item)) { why = Why.SrcGone; return Outcome.Drop; }
...
int room = item.m_shared.m_maxStackSize <= 1
    ? tInv.GetEmptySlots()          // non-stackables: count empty slots
    : Router.Room(tInv, item);      // stackables: partial-stack space + empty slots
if (promised.TryGetValue(tgt, out var already)) room -= already;
if (room <= 0) { why = Why.NoRoom; return Outcome.Retry; }   // may drain later in the run
```

`Router.Room` is the executor's whole theory of "does it fit"
([Router.cs:88](../src/ChestButler/Core/Router.cs:88)):

```csharp
internal static int Room(Inventory inv, ItemDrop.ItemData item)
{
    int max = item.m_shared.m_maxStackSize;
    if (max <= 1) return inv.GetEmptySlots() > 0 ? 1 : 0;
    return inv.FindFreeStackSpace(item.m_shared.m_name, item.m_worldLevel)
           + inv.GetEmptySlots() * max;
}
```

Two different room models now exist: the planner's slot ledger (evictions free space) and this
per-move live check (only what is empty *right now* counts). The retry queue plus
evict-before-fill ordering is what's supposed to reconcile them.

### 4.2 The handoff to MUC — and what we never check

If all guards pass ([Organizer.cs:744](../src/ChestButler/Core/Organizer.cs:744)):

```csharp
if (!tgtNv.IsOwner()) tgtNv.ClaimOwnership();

// exactly Puller's transfer primitive — the ONLY sanctioned write path
var request = ContainerHandler.RemoveItemFromChest(
    src, item, tInv, new Vector2i(-1, -1),
    tgtNv.GetZDO().m_uid, amount, null);

requestId = request != null ? request.RequestID : 0;
```

And back in the coroutine ([Organizer.cs:585](../src/ChestButler/Core/Organizer.cs:585)):

```csharp
if (outcome == Outcome.Issued)
{
    ...
    movedItems += amount;              // ◄◄◄ counted as MOVED at ISSUE time
    targetsHit.Add(pm.Move.Target);
```

Completion is detected by the request disappearing from MUC's queue
([Organizer.cs:827](../src/ChestButler/Core/Organizer.cs:827), `CountOutstanding`):

```csharp
bool stillQueued = PackageHandler.GetPackage<RequestChestRemove>(o.RequestId, out var pkg) && pkg != null;
if (!stillQueued)
{
    ReleasePromise(promised, o.Target, o.Amount);   // the fa50c09 fix — correct
    outstanding.RemoveAt(i);
    continue;
}
```

**This is the hole.** "The response arrived" is treated as "the move landed." The response
payload — did the server actually remove the items? how many? did the target-side add succeed, or
did MUC put the items *back* — is never read. `movedItems` was already counted at issue.
`"0 request(s) timed out"` in your log therefore means only *the server answered everything*; it
says nothing about what the answers were. The screen message "Organized 34 items" is a claim about
requests **sent**, not items **moved**.

## 5. The suspects, ranked

### #1 — "Issued" is not "landed": a rejected move is invisible and immortal

**Mechanism.** Some move is rejected on the far side — server-side source removal fails, or the
target can't accept at apply time and MUC compensates by returning the items to the source. The
response arrives (so: no timeout, promise released, request "complete"), the executor counts it as
moved, the world is unchanged. Next press: census sees the same items in the same place → the
allocator, which is deterministic, builds the **identical plan** → the same move fails the same
way. Forever.

**What it explains.** Anomaly B exactly (identical plans, "0 skipped", no convergence). And via
evict-before-fill (§3.2), Anomaly C too: if the 3 immortal moves are *evictions out of* the 2
chests that the 8 `NoRoom` moves want to *fill*, one silent failure produces both signatures with
number-for-number stability across presses. It may also explain the 1050-item reappearance if the
failure mode is "applied locally, reverted by server state" rather than "rejected outright."

**Status.** The code hole is certain (no response inspection). What's *not* yet established is
which MUC failure path is being hit — that's the agents' assignment (they're reading the actual
MUC 0.6.1 source).

### #2 — Local/server inventory divergence (ZDO ownership)

Vanilla `Container.Save` is owner-gated: a client that writes an inventory it doesn't own changes
its local copy only, and the server's authoritative ZDO state wins on the next sync. We
`ClaimOwnership()` on targets before issuing — but a claim is a race, not a lock; the server (or
its periodic ownership reassignment) can take it back mid-round-trip. If any of our target-side
adds applied only locally, then: our client sees chests as fuller than the server does (→ stuck
`NoRoom=8` against phantom contents), and items we "moved" reappear at their server-side positions
when zones resync (→ the 1050). This is suspect #1's evil twin — same hole, different leak.

### #3 — Planner/executor room-model mismatch

Even with perfect networking the two models can disagree: `Router.Room` counts partial-stack space
via `FindFreeStackSpace(name, worldLevel)` — the same merge-key dimensions the planner uses, but
the planner *also* assumes eviction ordering that the executor's per-move check can't see, and
non-stackables use `GetEmptySlots()` which is blind to evictions entirely. A chest that is full
*until its own eviction lands* will bounce fills for a full network round-trip; the settle-gate
handles that only if the eviction *eventually* lands. This suspect can't produce identical numbers
across presses **by itself** (the world would still drift toward converged) — it needs #1 or #2 as
the engine. Filed as a contributing factor, not the root.

### #4 — The background sorter fighting Organize

`Sorter: ON` was live the whole session. The sorter tick moves stacks out of sorter chests on its
own schedule, concurrently with Organize's coroutine. That's the obvious reading of `SrcGone=3`
on press 1 (a planned source stack vanished mid-run — the sorter got there first) and it churns
target room under the executor's feet. Real, but it can't explain identical 3-move plans whose
source is an ordinary chest, and it can't explain 1050 items. Noise, not the signal.

## 8. Verdicts (agent panel, adversarially verified against MUC 0.6.1 decompile)

**Root cause 1 — CONFIRMED (suspect #1).** MUC 0.6.1 "completes" a `RequestChestRemove` without
moving anything via several silent paths, and the executor cannot see any of them:

- **Dummy decline.** `RemoveItemFromChest` returns a *non-null dummy* request — `RequestID == 0`,
  no RPC sent, nothing changed — when the **source** container's ZDO has no owner (or the
  drag-amount clamp hits 0). `RequestID` is only ever assigned in `InventoryPreview.AddPackage`,
  which the decline paths never reach. The old code conflated `RequestID == 0` with "applied
  synchronously" and counted the items as moved. Hence "0 timed out": a declined move never
  creates an outstanding request at all.
- **Remote failure.** On the RPC path, the owner side answers `Success=false, Amount=0` when the
  stack isn't at the expected position (or a fallback when the addressee isn't owner) — and the
  requester-side handler removes the package from `PackageHandler` *before* checking `Success`.
  Queue departure is byte-identical for success and failure.
- **Partial.** `response.Amount` can be less than requested; it was never read.
- Also verified: MUC has **no compensation path** — a failed remove leaves everything in place
  (hence bit-identical replans), and a *successful* remove whose target add overflows drops the
  remainder at the player's feet with a `$msg_dropped` HUD message.

**Root cause 2 — CONFIRMED (the deterministic driver).** `TryIssue` ownership-gates and claims
only the **target**; the **source** — the endpoint MUC's remove actually executes on — was never
checked. Vanilla `ZDOMan.ReleaseNearbyZDOS` instantiates ZDOs over `activeArea` (2 zones) but
assigns ownership only over `activeArea − 1` (1 zone): on a dedicated server, chests in the outer
band (~64–160 m out, within Organize's 128 m radius) are plannable but **permanently owner==0**.
Every remove from such a chest is a dummy decline, every press, forever — the immortal
3-move/34-item source. Structurally invisible: skip diagnostics only tally Retry/Drop, and these
moves were counted "Issued".

**Root cause 3 — the NoRoom=8 stalemate is downstream of 1+2** (suspect #3 as predicted in §3.2):
the planner's ledger credits slots freed by evictions; phantom evictions never free them; the
fills burn their 2 attempts at an instantly-"settled" world (phantom moves are never outstanding)
and skip. Same numbers every press because nothing ever changes.

**The 1050-item event — suspect #2 REJECTED.** Not a server revert: presses 2–4 genuinely shrank,
the organized targets kept their contents (or NoRoom=82 couldn't happen), and the event came with
`home markers: 1 claimed` — a *new* chest entering allocation. It was **late census growth**:
press 1 ran ~9 s after spawn while the base was still streaming in; a 17-chest wing finished
instantiating by 15:19:13. The census only sees instantiated chests.

**Suspect #4 (sorter) REJECTED** for the cycle: the sorter only moves items *out of* sorter chests
it owns — it cannot refill the stuck source or produce identical censuses. Its only confirmed
contribution is press-1 concurrency noise (`SrcGone=3`).

## 9. The fix (this commit)

1. **Claim unowned sources** — `TryIssue` mirrors the target gate: `if (!srcNv.HasOwner())
   srcNv.ClaimOwnership()`. This flips MUC onto its synchronous owner path for outer-band chests;
   the removal applies and persists the same frame.
2. **Detect declines** — a non-null request with `RequestID == 0` returns `Why.Declined`
   (retryable, visible in the breakdown), never a move.
3. **Credit on response, not on issue** — a Harmony postfix on MUC's
   `RPC_RequestItemRemoveResponse` records `Success`/`Amount` per request id
   ([MucResponsePatches.cs](../src/ChestButler/Patches/MucResponsePatches.cs) →
   [MucResults.cs](../src/ChestButler/Core/MucResults.cs)); `CountOutstanding` settles the books
   from the recorded verdict. `movedItems` now counts **confirmed** transfers (at the owner's
   actual amount), `Success=false` shows up as `RespFailed` in the skip breakdown, and the run
   waits for all responses before reporting.
4. **Census visibility** — every BuildPlan log line now carries the census chest count, so a base
   still streaming in is visible across presses ("census 47 chest(s)" growing to 64).

Prediction for the next staging run: the previously-immortal moves either land (source claimed →
synchronous) or appear as `Declined`/`RespFailed` in the breakdown — nothing silent remains. A
press after a settled press must plan **0 moves**.

**Verified in-game 2026-08-10** (build `f12de9ec`, fresh world reset, census stable at 110 chests
on every plan): press 1 issued 361 moves, **confirmed 5743 items** (0 timeouts, 0 unverified,
residue `SrcGone=3 NoRoom=6` = 95 items of sorter-concurrency noise); press 2 swept exactly that
residue — 6 moves, 15 items, all confirmed, 0 skips; **press 3 planned 0 moves.** No `Declined`,
no `RespFailed`: the source-ownership claim turned every former phantom into a real move. The
press-2 convergence contract holds on the dedicated server.
