# MultiUserChest on Valheim 1.0 — fork, test, upstream PR

ChestButler is 1.0-clean after one diagnostic-only fix. The thing that actually breaks chests on
1.0 is **MultiUserChest 0.6.1**, and ChestButler cannot ship until a working MUC is installable.
This is the plan for fixing it, proving the fix in game, and getting it back upstream.

Upstream state (2026-09-11): no open pull requests. Issue
[#16 "Valheim 1.0.7 incompatibility"](https://github.com/MSchmoecker/No-Chest-Block/issues/16) is
open with no replies and is break B below.

## 1. What is actually broken — three independent breaks

### Break A: `TypeLoadException` aborts `PatchAll` partway through

```
TypeLoadException: Could not resolve type with token 0100005a
                   from typeref (expected class 'Element' in assembly '')
  at HarmonyLib.PatchTools.GetPatchMethod
  at HarmonyLib.Harmony.PatchAll ()
  at MultiUserChest.Plugin.Awake ()
```

Valheim 1.0 promoted the nested `InventoryGrid.Element` to a top-level `InventoryElement`.
`Harmony.PatchAll()` reflects over every type in the assembly and reads its methods' attributes, so
a *signature* mentioning the missing type is fatal — the patch class never has to run.

`PatchAll` walks MUC's eight patch classes in metadata order and `InventoryGuiPatch` is sixth:

| # | patch class | applied on 1.0? |
|---|---|---|
| 1 | `ItemDrawerCompat` | yes |
| 2 | `QuickStackPatch` | yes |
| 3 | `ContainerPatch` | **yes** — and it carries break B |
| 4 | `GamePatches` | yes |
| 5 | `HumanoidPatch` | yes |
| 6 | `InventoryGuiPatch` | **throws here** |
| 7 | `InventoryPatch` | no |
| 8 | `PickupPatch` | no |

### Break B: MUC answers "open chest" under the pre-1.0 RPC name (issue #16)

1.0 renamed `Container`'s per-object RPC registrations:

| 0.221.12 | 1.0.7 |
|---|---|
| `RequestOpen` | `RPC_RequestOpen` |
| `OpenRespons` | `RPC_OpenResponse` |
| `RequestTakeAll` | `RPC_RequestTakeAll` |
| `TakeAllRespons` | `RPC_TakeAllResponse` |
| `RPC_RequestStack` | unchanged |
| `RPC_StackResponse` | unchanged |
| — | `RPC_Discovered` (new) |

`ContainerPatch` replaces vanilla's `RPC_RequestOpen` on the chest owner with its own version, and
that version replies with the hard-coded string `"OpenRespons"`. RPCs travel as
`GetStableHashCode(name)`, and `GetStableHashCode("OpenRespons") = -1556840686` — checked against the
real 1.0 `assembly_utils`, not just a reimplementation. The requesting client no longer registers
that name, so `ZNetView.HandleRoutedRPC` logs

```
Failed to find rpc method -1556840686
```

and drops the reply. **The chest never opens.** That is issue #16 verbatim, and it fires on every
container MUC handles, whether or not ChestButler is installed.

The vanilla side is otherwise unchanged: 1.0's `RPC_RequestOpen` runs the same owner check, in-use
check (including the wagon), `CheckAccess`, `ForceSendZDO`, `SetOwner`, reply sequence as 0.221.12 —
only the log format and the RPC name differ. So MUC's reimplementation stays faithful once the name
is fixed.

### Break C: Harmony targets that moved (found by the first in-game test)

The first test build — A and B fixed — still aborted `PatchAll`, one step later:

```
HarmonyException: Ambiguous match for HarmonyMethod[(class=Inventory, methodname=Load, type=Normal, args=undefined)]
```

Harmony resolves `[HarmonyPatch]` targets by name at runtime, so a new overload or an appended
parameter breaks a patch that still compiles:

| MUC patch | target as written | in 1.0.7 | result |
|---|---|---|---|
| `InventoryGuiPatch.InventorySelectSameItemAfterLoad` | `Inventory.Load`, name only | `Load(ZPackage, bool)` added beside `Load(ZPackage)` | ambiguous match — `PatchAll` aborts |
| `InventoryPatch.AddItem1Prefix`, `InventoryPatch.RemoveLogging` | `AddItem(ItemData, int, int, int)` | now `AddItem(ItemData, int, int, int, bool skipValidPositionCheck = false)` | undefined target — the next abort in line |
| `ItemDrawerCompat.PreventItemAdd` (only with ItemDrawers installed) | same `AddItem` overload | same | same, for ItemDrawers users |

Chests opened in that build, which confirmed B's fix: `ContainerPatch` runs before the abort. But
Harmony resolves every target in a class before it patches any of them, so all of
`InventoryGuiPatch` stayed off — including the transpiler that lets a non-owner keep a chest open —
along with `InventoryPatch`, whose prefixes route a non-owner's adds and removes through MUC's
requests, and `PickupPatch`. Solo play looks fine in that state; two players in one chest do not.

### Why the first pass missed breaks B and C

Neither is visible to the compiler or to a Cecil reference scan, which both passed with B and C
still in the build: B is a string, and C is a method name inside an attribute that Harmony resolves
only at runtime. Two more checks now cover those classes.

**Harmony targets.** Every `[HarmonyPatch]` is resolved the way Harmony does it: declared methods
only, a name-only target must match exactly one overload, a typed one must match the signature
exactly. Every patch parameter must then bind to a parameter or field of the resolved original, and
each transpiler's IL pattern is checked against the 1.0 method body — `UpdateContainer` still has
`ldarg.0; ldfld m_currentContainer; callvirt IsOwner` exactly as in 0.221.12, and the new
`AddItem(…, bool)` still calls `ZLog.Log`. Run first against stock 0.6.1 on 0.221.12 as a control,
where it comes back clean. After the fix every MUC target resolves and binds, and so do all nine of
ChestButler's.

**String literals.** Every string literal in MUC (upstream `HEAD`) and in ChestButler, intersected
with the 146 string literals vanilla dropped between 0.221.12 and 1.0.7:

| | hits |
|---|---|
| MUC | `OpenRespons` — break B, and the only one |
| ChestButler | `" released"` — its own log text in `Organizer.cs:495`, false positive |

ChestButler registers and invokes no RPCs of its own; every transfer goes through MUC's routed RPCs
(`MUC_*`), whose names MUC owns. So this class of break cannot reach ChestButler directly.

## 2. The fix (done, builds clean)

Everything else 1.0 changed under MUC — `SEMan.AddStatusEffect`, `Character.Message`,
`EffectList.Create`, three other `Inventory.AddItem` overloads — only gained *appended* parameters,
so those call sites still compile untouched.

### `Patches/InventoryGuiPatch.cs` — break A

| was | now | why |
|---|---|---|
| `InventoryGrid.Element` (3 refs) | `InventoryElement` | nested type promoted to top level |
| `element.m_pos` | `element.Position` | field replaced by a property |

### `Patches/ContainerPatch.cs` — break B

| was | now | why |
|---|---|---|
| `"OpenRespons"` (3 sends) | `nameof(Container.RPC_OpenResponse)` | the actual fix |
| `"RPC_StackResponse"` (3 sends) | `nameof(Container.RPC_StackResponse)` | unchanged in 1.0, same hazard |

1.0 registers every `Container` RPC under its handler's method name, so `nameof` turns the next
rename into a compile error instead of another silent runtime break. MUC already uses `nameof` for
the same members in its `[HarmonyPatch]` attributes.

### Harmony targets — break C

| file | target was | now |
|---|---|---|
| `Patches/InventoryGuiPatch.cs` | `Inventory.Load` (name only) | `Inventory.Load(ZPackage)` |
| `Patches/InventoryPatch.cs` (2 patches) | `AddItem(ItemData, int, int, int)` | `AddItem(ItemData, int, int, int, bool)` |
| `Patches/Compatibility/ItemDrawerCompat.cs` | `AddItem(ItemData, int, int, int)` | `AddItem(ItemData, int, int, int, bool)` |

`Load(ZPackage)` is the overload every vanilla caller uses (`Container.Load`, `Player.Load`,
`ZDOMan.ConvertInventories`), so the postfix fires exactly where it did on 0.221.12. Prefix
parameters bind by name (`item, amount, x, y`), so the appended `skipValidPositionCheck` needs no
change to any patch body.

### `Helper/InventoryHelper.cs` — the new `cheated` parameter

`Inventory.AddItem(…)` gained a required `bool cheated` before its optional tail:

```csharp
Boolean AddItem(String name, Int32 stack, Single durability, Vector2i pos, Boolean equipped,
                Int32 quality, Int32 variant, Int64 crafterID, String crafterName,
                Dictionary<string,string> customData, Int32 worldLevel, Boolean pickedUp,
                Boolean cheated, Boolean skipValidPositionCheck = false)
```

1.0 also added the backing field `ItemDrop.ItemData.m_cheated`. MUC's `WriteItemToPackage` /
`LoadItemFromPackage` are a hand-rolled symmetric serializer, so the field has to be added there or
a cheat-spawned item silently loses the flag every time it crosses a chest boundary. Two lines, one
on each side, plus passing it through to `AddItem`.

**This is a wire-format change and it forces a version bump.** MUC declares
`[NetworkCompatibility(EveryoneMustHaveMod, VersionStrictness.Patch)]`, so Jotunn rejects a peer
whose patch version differs. Shipping a new wire format under the *same* `0.6.1` string would let a
stock peer connect and then mis-parse every transfer. Bump `ModVersion` **and** `manifest.json` to
`0.6.2` in the same commit as the serializer change, never separately.

## 3. Building it (the upstream project does not build offline)

The fork working copy is **`C:\Users\Light\projects\No-Chest-Block`** — a clone of upstream with the
fix applied and no remote of our own yet.

Upstream is a `packages.config` project whose publicizer comes from the `JotunnLib` NuGet package.
Two local pieces stand in for that. Both live under `build/`, outside upstream's own tree, and
**neither belongs in the PR**:

1. `build/publicize.ps1` — Mono.Cecil pass (Cecil comes from `BepInEx/core/`) that makes every
   type, field and method in `assembly_valheim`, `assembly_utils` and `assembly_guiutils` public,
   writing them into `build/pubmanaged/` beside unmodified copies of the rest of `Managed/`.
2. `build/MUC.Build.csproj` — SDK-style project that compiles `../MultiUserChest/**/*.cs` against
   that folder and the DLLs already in the BepInEx profile. No package restore, so it works
   offline. `out/`, `build/pubmanaged/` and `build/obj/` are in `.git/info/exclude`.

Build:

```bash
dotnet build build/MUC.Build.csproj -c Release --no-incremental \
  -p:PUB_MANAGED="$PWD/build/pubmanaged" \
  -p:BEPINEX_CORE="$PROFILE/BepInEx/core" \
  -p:JOTUNN_DLL="$PROFILE/BepInEx/plugins/ValheimModding-Jotunn/Jotunn.dll"
```

Output: `out/MultiUserChest.dll`.

## 4. Phase 3 — prove it in game (**gate: nothing below starts until this passes**)

Valheim must be closed; the profile DLL is locked while it runs.

**Setup** — `Test` profile only, as always:

- `build/install-test-profile.sh` in the fork — backs up the stock DLL once as
  `MultiUserChest.dll.0.6.1.bak`, installs `out/MultiUserChest.dll`, and overwrites the Thunderstore
  Mod Manager cache copy too, because TMM redeploys from its cache on every launch.
- `./build.sh` in ChestButler — installs the 1.0 ChestButler build the same way.

**Both mods must be enabled in the mod manager before installing.** `build.sh` copies
`ChestButler.dll` in unconditionally, so over a disabled mod it lands beside the manager's `.old`
copy, where BepInEx loads it while the manager still shows the mod as off. The MUC install script
refuses a disabled mod instead.

MUC handles every container except OdinShip ones and ZDOs flagged `MUC_Ignore`, so any chest
exercises break B. Use player-built chests for T4 anyway — those are what ChestButler sorts.

**T1 — the load itself.** `LogOutput.log` shows `Loading [MultiUserChest 0.6.2]` with **no**
`TypeLoadException` and no Harmony exception of any kind — break C announced itself as one —
followed by `ChestButler 2.0.x loaded`.

**T2 — vanilla chest behaviour, single player.** Open a chest, move items both directions, drag a
partial stack, Stack All, Take All, close. `Player.log` must contain **no**
`Failed to find rpc method -1556840686` (break B). This is also the half that `InventoryGuiPatch`
owns and that breaks A and C left dead — the primary regression surface.

Do not chase `Failed to find rpc method 327122920`. That hash is `"discovered"`, and it is a
vanilla 1.0.7 bug that shows up with or without mods: `Container.Interact` sends `"discovered"`
while `Container.Awake` registers the handler as `RPC_Discovered`, so the owner drops it and the
chest's per-player discovered flag is never recorded. It only fires on containers with a discover
stat (treasure/dungeon chests).

**T3 — MUC's own feature.** Two clients against the `Karnimor Server` profile, both in one chest at
once: simultaneous takes of the same stack, one taking while the other deposits. Nobody dupes,
nobody loses a stack, neither client gets locked out. Issue #16 was reported on a dedicated server,
where the server owns the chest and sends the open reply — this is its reproduction. It is also the
only test that exercises what break C switched off.

**T4 — ChestButler's transfer paths**, the four that call into MUC: sorter chest routing, Pull,
Gather, and an Organize run. Then the acceptance property that already has a name in
`docs/2.0-test-script.md` §W1-G3: **a second Organize press must move nothing.**

**T5 — dedicated server.** Repeat T4 against `Karnimor Server` with the server also on the rebuilt
MUC. Confirm the `[organize] skip breakdown:` line reports `activeAreaLoaded=` /
`outsideActiveArea=` — the two fields that replaced 1.0's removed `m_activeArea` /
`m_activeDistantArea` — and that `OwnerHeld` skips are not systematically nonzero.

**T6 — negative control.** Put `MultiUserChest.dll.0.6.1.bak` back, launch, confirm the
`TypeLoadException` and the `-1556840686` line both return. Proves the fix is what fixed it.

## 6. Phase 5 — unblocking users (decide after the PR is open)

Upstream's last commit is 2025-02-09, so the PR may sit. ChestButler's own 1.0 release is blocked
until players can install a working MUC. Two ways out, and this is a call to make with the PR
already open rather than now:

- **Publish a fork package** (`EladKarni-MultiUserChest`, MIT, attributed, description pointing at
  the open PR) and repoint ChestButler's manifest dependency at it. Users are unblocked the day it
  goes up; the cost is a second package to keep alive and a fragmented ecosystem until the PR
  lands, after which the fork is deprecated back to upstream.
- **Wait for upstream** and hold ChestButler's 1.0 release. No fragmentation, no timeline.
