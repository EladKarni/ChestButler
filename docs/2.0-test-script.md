# W1 — Organize v2 (commit 354defd): whole-base volume-aware allocation

> ⚠ **Blocked** — see the known Organize bug above. Run these only after the allocator fix; W1-G1 is the test that catches it.

## What it does as built

Organize v2 replaced the old "move items that already have a home" sweep with a two-stage pipeline. `Core/Organizer.BuildPlan` (Unity adapter) snapshots every accessible player-built Container within `[Sorting] Radius` (128 m) of the chest you clicked — including Sorter chests, which are sources but never targets — does ONE spatial station pass for the whole run (`Stations.HitsAround` + `GroupsNear`, replacing the per-chest `GroupsForChest` scan), and classifies every distinct item norm into exactly one bucket key in this order: (1) an explicit pin/sign token on any chest that can receive → `item:<norm>`; (2) an `[ItemGroups]` category via `Groups.FirstGroupFor` in the fixed `GroupTables.GroupOrder`; (3) non-stackable and `IncludeGear` on → `gear:weapons` / `gear:armor` / `gear:tools` / `gear:misc` by `m_itemType` with `ToolTokens`/`WeaponTokens`/`ArmorTokens` overriding first; (4) ungrouped stackable → `item:<norm>` provisionally. `Core/OrganizePlanner.Plan` (pure, no Unity/config/clock) then folds any un-anchored `item:` bucket needing ≤ `MiscPromoteSlots` (24) slots into a single `misc` bucket, computes exact slot demand per bucket (stacks that cannot merge across NG+ world levels get distinct identities like `iron#2`), allocates chests largest-demand-first from ONE shared capacity ledger — anchors first in `Pin > Sign > Station > Home` order, then claiming free chests, preferring genuinely empty ones and measuring distance from the bucket's own primary home rather than from the clicked chest — computes the final distribution and emits only the DIFF, with evictions ordered before fills. Chests the allocator claims itself get a `psort_home` ZDO string (`Filters.GetHome/SetHome/ClearHome`, key `psort_home`), written at confirm time, read back as the WEAKEST anchor kind so the fill order is identical across runs; that plus the diff is what makes a second press on a tidy base move zero items. A chest labelled `sort: off` is excluded as source AND target and its slots are not counted as capacity; a `Manual` chest (now toggleable on an EMPTY chest, §15.10) is excluded as target only; Sorter chests are excluded as targets. The UI is preview-then-confirm inside a 5 s window, and the confirm press RE-PLANS rather than executing the previewed plan. Execution is a coroutine with a real per-second token bucket (`[Organize] MovesPerSecond`, default 25) instead of the deleted per-frame `MovesPerTick`, a `MaxMovesPerRun` cap (500), 2 attempts per move, abandonment of the whole retry queue as soon as a full drain issues nothing, an 8-deep outstanding-request ledger with a 10 s deadline read through MUC's `PackageHandler`, and full re-validation of both endpoints (ZDO validity, ward, container access, ZDO ownership, room) immediately before every transfer. `Core/Throttle.cs` measures the mod's own cost and scales rates down only. Every plan logs `[organize] BuildPlan took N ms: …`.

## W1-G1 — First Organize on a messy base — preview → confirm counts are honest, BuildPlan is instrumented

**Why:** Nothing in W1 has ever executed in a game. This proves BuildPlan/classify/allocate/Execute work at all end to end, that the confirm-time RE-PLAN (§16.2.6 fix) yields the same numbers when nothing changed, that the `misc` fold and the three gear buckets form, and it captures the `BuildPlan took N ms` figure roadmap §9 item 8 asks for.

**Setup**

- Launch the Test profile. Confirm the log line `ChestButler 1.1.2 loaded` — the version files were deliberately not bumped; this IS the 2.0 code.
- New single-player world. Open the console with F5. Server_devcommands has `Automatic devcommands = true`, so commands should already work; type `devcommands` if any is refused.
- Type `god`. Then `debugmode` for free building. (If the hammer still demands materials or a station, `nocost` also works, but note its config has `Limit recipes to station with nocost mode = true`, so you would then need a workbench in range.)
- Pick flat open ground at least 200 m from any other chest you own — `[Sorting] Radius` is 128 m and Organize sweeps every accessible player-built container inside it.
- Build a Workbench, then walk 12-15 m away and build the chests there. `[Stations] $piece_workbench = wood, hides` and `[Organize] StationRange = 8`, so a workbench within 8 m of a chest silently makes that chest an anchor for wood/hides. Remove the workbench once the chests are placed if you prefer.
- Build 12 vanilla REINFORCED chests (`piece_chest`) about 2 m apart: one called S (the sorter), one called D (dump), and E1..E10 left completely empty. Do NOT use the 'Sorter Chest' piece in the Furniture tab — that is W3's piece, it is a Sorter out of the box, and Sorters are never Organize targets.
- Open S. The toolbar sits at the bottom-left of the chest panel. Click the leftmost button reading `Sorter: OFF`. It must change to `Sorter: ON` and a centre message must read `Sorter enabled. Contents distribute when the chest is closed`. The toolbar on S now shows only [Sorter: ON] [Organize].
- Spawn the mess (auto pick-up is on, so walk over the drops): `spawn Wood 200`, `spawn FineWood 100`, `spawn Stone 200`, `spawn Flint 50`, `spawn Bronze 60`, `spawn Iron 60`, `spawn Carrot 20`, `spawn Honey 20`, `spawn DeerHide 40`, `spawn LeatherScraps 40`, `spawn Resin 40`, `spawn Feathers 40`, `spawn GreydwarfEye 40`, `spawn Dandelion 10`
- Spawn the gear: `spawn SwordBronze 1 1`, `spawn AxeBronze 1 1`, `spawn Club 1 1`, `spawn BowFineWood 1 1`, `spawn ArmorBronzeChest 1 1`, `spawn HelmetBronze 1 1`, `spawn CapeDeerHide 1 1`, `spawn Hammer 1 1`, `spawn Hoe 1 1`, `spawn Cultivator 1 1`, `spawn PickaxeBronze 1 1`
- Drag everything into S until S is full, remainder into D. Leave E1..E10 completely empty. Vanilla has no deposit-all, so this is stack-by-stack.
- Open the log for tailing: ...\Thunderstore Mod Manager\DataFolder\Valheim\profiles\Test\BepInEx\LogOutput.log

**Steps**

- Open S. Click `Organize` (first press). Write down the exact centre message, specifically N (items) and M (chests).
- Do NOT close the chest. Between ~0.5 s and 5 s later, click the same button again — its label should now read `Confirm?`.
- Keep S open until the result centre message appears.
- Grep the log for `[organize]`.
- Open D and E1..E10 and record exactly what landed in each.

**Expected**

- First press: the Organize button label changes to `Confirm?` and the centre message reads `Organize: move N items across M chests - press again to confirm`. With 10 spare empty chests there must be NO `(K won't fit - add more chests)` clause.
- The log contains TWO `[organize] BuildPlan took` lines per Organize cycle — one for the preview press and one for the confirm-time re-plan — and both report the same move count, because nothing changed in between.
- `[organize] plan ready: N items -> M chest(s) from S source(s); awaiting confirm` carries the same N and M as the centre message.
- `[organize] home markers: C claimed, 0 released` appears at confirm time (markers are written at Execute, never at preview). C should be >= M: every bucket claims a chest, and a source chest can be claimed without receiving anything.
- `[organize] executing K move(s)` then `[organize] issued K move(s) covering N item(s) into M chest(s); skipped 0 move(s) covering 0 item(s); 0 request(s) timed out; throttle scale 1.00`. The item count and chest count must equal the preview's N and M exactly.
- Result centre message: `Organized N items into M chests` with no `(… could not move)`, no `; … had no room - add more chests`, no `; … transfer(s) timed out`, and no `. Press Organize again to continue`.
- Physically, nine distinct chests, one per bucket: wood+finewood; stone+flint; bronze+iron; carrot+honey; deerhide+leatherscraps; resin+feathers+greydwarfeye+dandelion ALL TOGETHER in one chest (that is the `misc` fold — each is an ungrouped stackable needing <= MiscPromoteSlots=24 slots); and three separate gear chests.
- S is empty or nearly so. Record the `BuildPlan took N.N ms` value and the chest count — this is roadmap §9 item 8.

**If it fails:** No `[organize]` lines at all → the button is not wired or GuiPatch did not build the toolbar. Confirm-press item count differs from the preview → the re-plan is seeing a different world, almost always a second Sorter chest ticking underneath you. Non-zero `skipped N move(s)` on a static single-player base → TryIssue's re-validation (ZDO owner / IsInUse / ward / Room) is rejecting legitimate moves. `issued` item count larger than the preview → the plan is double-counting stacks. Everything piling into one chest → bucket keys are collapsing.

## W1-G2 — Gear is filed into weapons / armor / tools, and pickaxes land with the tools

**Why:** Core/Gear.cs maps `m_itemType` to three buckets and lets `[Organize] ToolTokens` override the type. §16.4.4 predicted pickaxes misfiling with swords because there is no Pickaxe ItemType — the override is the fix and has never run against real ItemDrop data. Also flushes out any item type with no gear bucket.

**Setup**

- G1's end state, untouched.
- Optional extras to widen the type coverage: `spawn PickaxeAntler 1 1`, `spawn AxeIron 1 1`, `spawn ShieldWood 1 1`, `spawn BeltStrength 1 1`, `spawn Torch 1`, `spawn TrophyBoar 3`. Put them into S.

**Steps**

- Open the three gear chests from G1 and record their contents.
- If you spawned the extras, open S, press Organize, and confirm.
- Re-open the three gear chests plus whatever chest the trophies went to.
- Grep the log for `has no gear bucket`.

**Expected**

- Weapons chest holds SwordBronze, AxeBronze, AxeIron, Club, BowFineWood, ShieldWood — and a Torch if you added one, because `ItemType.Torch` is explicitly mapped to `gear:weapons` in Gear.cs.
- Armor chest holds ArmorBronzeChest, HelmetBronze, CapeDeerHide, and BeltStrength (`ItemType.Utility` is mapped to armor).
- Tools chest holds Hammer, Hoe, Cultivator, PickaxeBronze, PickaxeAntler. THE PICKAXES MUST BE WITH THE TOOLS, not the swords — that is `[Organize] ToolTokens = pickaxe*` beating the item's own type, which is checked first in `Gear.BucketFor`. AxeBronze/AxeIron must stay with the weapons (`pickaxe*` is a prefix match and `axebronze` does not start with `pickaxe`).
- Trophies go to a `trophies` chest, NOT a gear chest — group matching (step 2) runs before gear classification (step 3), even though trophies are non-stackable.
- Any line `[organize] '<norm>' (item type <T>) has no gear bucket - filed under misc. Add it to [Organize] WeaponTokens/ArmorTokens/ToolTokens to place it.` names an unmapped type. Record them all; zero such lines with vanilla gear is a perfectly good result. Each such item ends up in the `gear:misc` bucket, which is a separate chest from `misc`.
- Each gear bucket gets its own chest even for one item — gear buckets are never folded into `misc` (FoldSmallTypeBuckets only touches `item:` keys). Note this if it looks wasteful; it is by design.

**If it fails:** A pickaxe in the weapons chest → the token override is not running before the ItemType map, or ToolTokens is empty in the config. Weapons/armor/tools sharing one chest → the three gear bucket keys are collapsing to one, or there were not enough free empty chests. Gear not moving at all → `IncludeGear` read as false, or the classify step is dropping non-stackables. Gear landing in `misc` rather than `gear:misc` → BucketKeys prefix handling is broken.

**Log lines**

```
has no gear bucket - filed under misc
[organize] BuildPlan took
[organize] issued
```

## W1-G3 — ACCEPTANCE — the second press must move nothing, and claimed homes must be visible

**Why:** This is the headline claim of Organize v2, and the notes say a non-zero second press is 'the headline bug'. It is also the only in-game check that the fixed fill order (anchor strength → priority → distance → uid) plus the diff step actually converge. Second: it teaches the tester the one available way to see a `psort_home` marker.

**Setup**

- G1/G2 end state. Do not touch anything, do not add items.

**Steps**

- Open S and press Organize exactly once. Read the centre message and watch the button label.
- Grep the newest `[organize] BuildPlan took` line.
- Press Organize once more (a third press) and record the same two things.
- Close S. Open every chest that received items in G1 and look at the toolbar.
- Open one chest that is still completely empty and look at the toolbar.

**Expected**

- Centre message `Nothing to organize` and the button label STAYS `Organize` (it must not change to `Confirm?`).
- Newest log line reads `[organize] BuildPlan took N.N ms: 0 move(s), 9 bucket(s), 0 item(s) with no room` — zero moves AND zero homeless.
- The third press behaves identically. Settling only on the third press is itself a failure — it is the exact symptom the notes describe from ordering the fill by 'who already holds the most'.
- Every chest that received items shows [Sorter: OFF] [Pin] [Clear]. On a chest with zero pins and Manual off, the presence of a `Clear` button is the observable proof that `psort_home` is set (GuiPatch: `showClear = n > 0 || manual || !IsNullOrEmpty(spec.Home)`), and the second button reading `Pin` rather than `Auto (n)` / `Manual` confirms there are no pins.
- The number of chests showing Clear should equal the `C claimed` from G1's `[organize] home markers: C claimed, 0 released` line.
- A still-empty spare chest shows only [Sorter: OFF] [Pin] — no Clear.

**If it fails:** Any non-zero move count on the second press → the fixed point is not holding; capture the BuildPlan line and note whether press three drops to zero. `0 move(s)` but a NON-ZERO `item(s) with no room` → two buckets ended up sharing one chest on run 1, the marker went to whichever bucket was enumerated first, and the other bucket is now permanently locked out of the chest its items are physically sitting in (it will report those items as homeless forever). No Clear button on chests that clearly received items → `psort_home` was never written, which means G4 will fail too and the fixed point is being held by geometry alone.

**Log lines**

```
[organize] BuildPlan took
0 move(s)
item(s) with no room
```

## W1-G4 — psort_home survives a relog, and it is load-bearing (negative control)

**Why:** `psort_home` is a ZDO string and nothing has ever proved it round-trips through a world save or that it does real work. The notes' offline negative control is 'settle 420 wood, then mine 2000 stone: with markers wood does not move, without them all 420 relocate' — this is that control, in-game, after a save/load cycle.

**Setup**

- G3 end state — the base is tidy and the second press already reported nothing.
- Write down EXACTLY which chest holds the wood and how much: e.g. 'E4: Wood 200, FineWood 100'. Also note which chest holds the stone.

**Steps**

- Save and quit to the main menu, then re-enter the same world and walk back to the base. (Teleporting 300 m away and back is a weaker substitute — the relog is the real test because it forces a save/load of the ZDO.)
- Open the wood chest. Does the `Clear` button still show?
- Open S and press Organize once.
- Now the negative control: `spawn Stone 1000` and put all of it into S (Stone stacks in 50s, so that is 20 slots and fits a reinforced chest).
- Press Organize, read the preview, then confirm.
- Re-open the wood chest and the stone chest(s).

**Expected**

- Step 2: the `Clear` button is still present on the wood chest → the marker survived the save/load. This is the single most important observation in this test.
- Step 3: `Nothing to organize` and `[organize] BuildPlan took N.N ms: 0 move(s), …` — the whole tidy base still converges after a reload.
- Step 5/6: `stone` is now by far the largest bucket by slot demand and is therefore allocated FIRST, but the wood chest carries `psort_home = wood` and `AnchorsAnotherLiveBucket` must refuse to let stone claim it. THE WOOD CHEST MUST BE IDENTICAL TO STEP 1 — zero wood items move.
- The stone fills its existing stone chest to capacity and spills into exactly one newly claimed empty chest; `[organize] home markers: 1 claimed, 0 released`.
- The result message's item count should be approximately the stone you just added, not the stone plus a relocated pile of wood.
- Press Organize once more: `Nothing to organize`.

**If it fails:** Clear missing on the wood chest after the relog → the ZDO string did not persist; every base will re-shuffle itself on every login. Clear present but wood still relocates → `AnchorsAnotherLiveBucket` is not blocking the steal (check that `AnchorKind.Home` is not being filtered out by the `kv.Value < AnchorKind.Home` guard). A full wood relocation is exactly the failure the offline negative control describes. `home markers: 0 claimed, N released` here → the allocator is clearing markers it should be keeping, which makes the fixed point one-shot.

**Log lines**

```
[organize] BuildPlan took
[organize] home markers:
[organize] issued
0 move(s)
```

## W1-G5 — Station affinity, and a category spilling outward from the STATION rather than from the chest you clicked

**Why:** Proves three things at once that only exist in v2: the single-pass station index (`BuildStationIndex` → `Stations.HitsAround` + `GroupsNear`) resolves a real `$piece_forge`; the Station anchor tier beats raw distance to the origin; and `PickFreeChest` measures 'nearest free chest' from the bucket's own primary home (`refChest = taken[0]`), not from the sorter. There is NO log line for station detection any more, so this can only be verified behaviourally.

**Setup**

- Open the metals chest from G1 (bronze+iron) and press `Clear` — centre message `Filters cleared`. This releases its claimed home so the forge chest becomes metals' only anchor. Leave the metal inside it; the allocator counts a chest full of movable items as empty anyway.
- About 30 m from S, build a Forge. `[Stations] $piece_forge = metals, ores`.
- Build chest F1 within 3 m of the forge, empty.
- Build chest F2 about 12 m from the forge — deliberately OUTSIDE `StationRange` (8 m) so it is not itself a station anchor — and further from S than F1 is.
- Make sure at least one empty chest (call it E_near) sits within 3 m of S.
- `spawn Bronze 300`, `spawn Iron 300`, `spawn Copper 300`, `spawn Tin 300`. Metal bars stack in 30s, so that is roughly 40 slots — more than one reinforced chest, which is what forces the spill. Split them between S and D.

**Steps**

- Open S, press Organize, note the preview.
- Confirm and wait for the result message.
- Open F1, F2, E_near and the old metals chest.
- Check the toolbars of F1 and F2.
- Press Organize once more.

**Expected**

- F1 fills with metals to capacity even though it is ~30 m from the chest you clicked and E_near is 3 m away. That is `AnchorKind.Station` beating distance in `CompareAnchors`.
- The overflow goes to F2 — the free chest nearest F1 — and NOT to E_near. E_near stays empty. This is the `refChest = taken[0]` behaviour: the category grows outward from its anchor.
- `[organize] home markers: 1 claimed, …` and opening F2 shows a `Clear` button (`psort_home = metals`).
- Opening F1 shows [Sorter: OFF] [Pin] with NO Clear. Station-derived anchors are re-derived every run and must never be marked — marking F1 would freeze its role after the forge is torn down.
- The old metals chest is drained.
- Final press: `Nothing to organize`.

**If it fails:** Metals landing in E_near instead of F1 → the station index is not resolving `$piece_forge`; the `CraftingStation.m_allStations` reflection or the `IsReal` ZNetView check is rejecting it, or `StationRange` is being applied to the wrong distance. # W2 — Gather (commit 0008732): Patches/GatherPatch.cs, Core/Gatherer.cs, Core/Gather.cs, Core/GatherMath.cs, Core/ContainerTracker.AccessibleNear

> ℹ **Two corrections since these were written:** the Gather button now sits **below** `Craft`, and the annotation renders as a compact green **`(N)`** — where the text below says `(N stored)` or `(N in storage)`, expect `(N)`.

## What it does as built

As built, W2 adds a second Harmony patch class on InventoryGui (separate from GuiPatch) that clones `m_craftButton` into a button named `psort_gather`, parents it to the craft button's parent, and parks it ONE BUTTON HEIGHT + 6 px DIRECTLY ABOVE the Craft button (not beside it — GatherPatch.cs:205). Its label is literally "Gather" or "Gather (N)" where N is the summed shortfall storage can cover. The requirement list is read out of the UI rather than the recipe: a prefix on `SetupRequirementList` clears the static `Needs` list and reflectively reads `m_selectedRecipe.Recipe.m_requireOnlyOneIngredient`; a postfix on `SetupRequirement(elementRoot, req, player, craft, quality, craftMultiplier)` records `needed = req.GetAmount(quality) * max(1, craftMultiplier)`, the player's count and the storage count, and appends `  (N stored)` in green (#9BE07A) to the row's `res_amount` TMP_Text when storage holds any. All of this runs EVERY FRAME the inventory is open, because vanilla `InventoryGui.Update` calls `UpdateRecipe` every frame — so `Gatherer.Sources()` (a full accessible-container scan at `[Sorting] Radius`, default 128 m) plus one `CountItems` per ingredient per chest happens per frame. Clicking Gather runs `GatherMath.Resolve` (per-ingredient `Gatherable = min(max(0, needed - inPlayer), inStorage)`; for require-only-one recipes it picks exactly ONE ingredient, or none if the player already has an option covered) and then `Gatherer.Pull`, which ranks chests richest-first (ties by ZDO uid), re-checks nview/`PlayerCanAccess`/`PrivateArea.CheckAccess` per chest, caps each issue by `Router.Room(playerInv, item) - promised`, and issues `ContainerHandler.RemoveItemFromChest(src, item, playerInv, (-1,-1), playerZDOID, amount, null)`. `sort: off` chests are excluded from `Sources()`; Manual chests are NOT. Two version-specific facts matter for testing: (1) the "craft multiplier" is not a quantity widget — it is HOLD LEFT SHIFT (`AltPlace`) / left-stick-click, which sets the multiplier to `InventoryGui.m_multiCraftAmount` (default 5) and only on the Craft tab (`itemData == null`), so Shift is a no-op on the Upgrade tab; (2) in single-player the local client owns the chest ZDO, so `RemoveItemFromChest` completes SYNCHRONOUSLY — items land in the inventory in the same click, and anything that does not fit is dropped on the ground by MultiUserChest, never destroyed.

## Gotchas / false negatives

- The craft multiplier is NOT a quantity selector widget. Vanilla computes it as `itemData == null && (ZInput.GetButton("AltPlace") || ZInput.GetButton("JoyLStick")) ? m_multiCraftAmount : 1`. AltPlace defaults to LEFT SHIFT (ZInput.AddButton("AltPlace", Key.LeftShift), rebindable) and m_multiCraftAmount defaults to 5. So you HOLD LEFT SHIFT to get x5, the Craft button label becomes 'Craft x 5', and it only works on the Craft tab — holding Shift on the Upgrade tab is correctly a no-op. Looking for a +/- amount widget will waste your time.
- In SINGLE-PLAYER the local client owns the chest ZDO, so ContainerHandler.RemoveItemFromChest runs the whole transfer synchronously (`if (container.m_nview.IsOwner())` branch) — items land in your inventory in the same click and the chest is already drained when you reopen it. Do not wait for a delay; if nothing arrived, nothing is coming.
- The 'Gathered N items (M types)' message and the '[gather] pulled N item(s)' log line are built from what was ISSUED, not from what arrived. A silent no-op still prints a confident number. Always diff the player inventory AND the chest.
- Items that do not fit are NOT lost. MultiUserChest's remove-response takes the toPos=(-1,-1) branch, does MoveItemToThis, and drops the remainder on the ground at your feet. Loot on the floor after clicking Gather is the signature of the 'promised' ledger failing, not of item loss.
- `debugmode` is fly mode only (Player.m_debugMode). The command that makes crafting/building free and unlocks EVERY recipe at EVERY station is `nocost` (Player.m_noPlacementCost). With nocost on, Player.GetAvailableRecipes ignores both known-recipes and station requirements and the Upgrade tab is always shown — that will silently invalidate any station-gating observation. Turn it off for G4/G6.
- A fresh character knows almost no recipes. Spawning materials with the `p` flag (e.g. `spawn Flint 100 p`) picks them up, which calls AddKnownItem and unlocks the matching recipes — that is why every setup uses `p`.
- The requirement panel only has 4 row slots. If a recipe has MORE than 4 ingredients, vanilla SetupRequirementList ROTATES which subset is displayed using `(int)Time.fixedTime % ...`, and GatherPatch clears and rebuilds Needs from whatever is displayed. On such a recipe the Gather count will visibly flicker and a click pulls only the currently-shown page. Avoid >4-ingredient recipes unless you are deliberately testing this.
- When NO recipe is selected (e.g. the Upgrade tab with nothing upgradeable in your inventory), vanilla UpdateRecipe takes an else-branch that calls HideRequirement directly and never calls SetupRequirementList — so GatherPatch's prefix never runs and Needs keeps the PREVIOUS recipe's data. Expect the button to hide; if it stays visible with a live count, that is a real defect, not a test artifact.
- All of this runs EVERY FRAME the inventory is open (InventoryGui.Update -> UpdateRecipe -> SetupRequirementList). That means one Gatherer.Sources() full container scan plus one CountItems per ingredient per chest per frame, at a 128 m radius. Watch the frame rate with the crafting panel open on a base with many chests; a stutter that only appears while the panel is open is this path.
- The button is placed one button-height + 6 px ABOVE the Craft button (GatherPatch.cs:205), not beside it, despite what gather-plan.md §1 says. Check for overlap with the ingredient rows and the Repair button rather than looking to the side.
- Chest labels look similar but mean opposite things to Gather: a chest with a nearby sign reading `sort: off` is NEVER read; a chest toggled to Manual (the 'Manual (n)' Pin-button state) IS read. The sign must be within 2.5 m of the chest AND that chest must be the nearest container to the sign, or the label binds to a different chest.
- Log levels in this profile are 'Fatal, Error, Warning, Message, Info' for both the console and LogOutput.log — LogDebug lines (the mod's '[ui] panel=...' and MultiUserChest's 'from is null') will NOT appear unless you add Debug to LogLevels in BepInEx.cfg.
- Plugin.Awake calls Harmony PatchAll BEFORE it logs 'ChestButler 1.1.2 loaded', so a missing load line means the patches threw — check that first in every session, and remember the version string reads 1.1.2 even though this is 2.0 code.
- Spawned chests work for these tests (they carry a Piece component and are Public), but a spawned `piece_chest_private` has no creator, so Container.CheckAccess fails and you cannot even open it — do not try to build the access test that way.

# W3 — Dedicated Sorter Chest (commit c272f5a; src/ChestButler/Core/SorterChestPiece.cs, registered from Plugin.Awake line 78)

## What it does as built

W3 adds exactly one thing to the game: a Jotunn `CustomPiece` named `ChestButler_SorterChest`, cloned by name from the vanilla prefab `piece_chest` (the REINFORCED chest — `piece_chest_wood` is the basic one), registered on `PrefabManager.OnVanillaPrefabsAvailable` and then immediately unsubscribed so a world change cannot double-register it. Its `PieceConfig` is: Name "Sorter Chest", Description "A reinforced chest that sorts its contents into nearby chests.", PieceTable "Hammer", Category "Furniture", CraftingStation "piece_workbench", requirements `Wood x10` and `BronzeNails x5` (both with recover=true, i.e. refunded on hammer-removal). No icon is set — it deliberately inherits the vanilla reinforced chest's icon, so it is visually identical to the vanilla chest in the build menu. Nothing else in the mod knows the piece exists: it is a `Container` with a `Piece`, so the existing `Container.Awake` patch registers it with `ContainerTracker` and attaches a `SorterBehaviour`, and the existing chest toolbar (`GuiPatch`) works unchanged. The only extra behaviour is a nested `[HarmonyPatch(typeof(Container),"Awake")]` postfix that, for containers whose ZDO prefab hash equals `"ChestButler_SorterChest".GetStableHashCode()` and whose ZNetView is valid AND owned locally AND whose `psort_defaulted` bool is not yet set, calls `SorterZdo.SetSorterDefault(c, true)` — which writes BOTH `psort_sorter = true` and `psort_defaulted = true`. That second key is the whole point: `psort_sorter` is a bool defaulting to false, so without the marker the chest would be re-flagged as a Sorter on every zone reload and would silently overrule a player who turned it off. Because it is a Sorter, the chest's toolbar shows exactly two buttons — `Sorter: ON` and `Organize` — and per handoff decision 4 the chest is excluded as an Organize *target* (`Organizer.BuildPlanInner`: `excludedTarget = SorterZdo.IsSorter(c) || spec.Ignore || spec.ManualOnly`) while remaining a *source* (`CandidatesWithDistance(..., excludeSorters: false)`). It is also never a push target for another sorter's tick (`ContainerTracker.Candidates` defaults `excludeSorters: true`). W3 adds no config keys of its own.

# W4 — gamepad support (commit 01767ae) + cross-cutting regression of shipped 1.1.x behaviour

## What it does as built

W4 does NOT re-enable UIGamePad (the roadmap's plan) — GuiPatch.MakeButton and GatherPatch.EnsureButton both still DestroyImmediate every UIGamePad on the cloned buttons. Instead, Core/GamepadNav.cs writes plain Unity Selectable navigation links: GuiPatch.LinkGamepadNav() runs at the very end of Refresh() (after button visibility settles) and chains the row [psort_toggle, psort_pin, psort_clear, psort_pull, psort_organize] left/right with Navigation.Mode.Explicit, skipping any button whose GameObject is inactive; then AttachRowToAnchor links the vanilla m_takeAllButton DOWN to the first live button (always the Sorter button) — but only if Take All's selectOnDown is currently null (onlyIfVanillaEmpty:true), logging "[gamepad] … left it alone" at Debug level if it is not. GatherPatch.RefreshButton() links psort_gather DOWN to m_craftButton unconditionally (onlyIfVanillaEmpty:false), so Craft gets selectOnUp = Gather. No ZInput, no key bindings, no hints. Config is one lazily-bound entry, [Gamepad] Enabled (default true), bound off Plugin.Instance.Config the first time GamepadNav.Enabled is read — i.e. the section does not exist in the .cfg until a chest has been opened once. Two consequences the plan doc does not state and that the tests below target: (1) both LinkRow and LinkVertical set navigation.mode = Explicit on the touched Selectables, and in Unity Explicit mode nulls every direction that is not explicitly assigned — so flipping the vanilla Take All and Craft buttons to Explicit destroys their Automatic left/right/up(/down) neighbours; (2) turning [Gamepad] Enabled off only makes the helpers return early, it never restores navigation already written, so the kill switch is only clean from a fresh game start. Nothing else in the mod changed for mouse/keyboard: onClick handlers, labels, PositionBar and all sorter logic are untouched by W4. The regression half of this plan covers the shipped 1.1.x behaviour that 2.0 could have broken, above all SorterBehaviour.FixedUpdate, which W1 edited to route its tick interval through Throttle.TransferInterval() and its 10 s per-item-type miss cooldown through Throttle.MissCooldown().

## Gotchas / false negatives

- Debug logging is OFF by default in this profile. BepInEx.cfg has LogLevels = Fatal, Error, Warning, Message, Info under BOTH [Logging.Console] (line ~75) and [Logging.Disk] (line ~101). The single most important evidence lines in this plan — '[sorter] routed …', '[gamepad] … left it alone' and '[ui] panel=' — are all LogDebug and will be completely invisible until Debug is added to both lines. A tester who skips this will report 'the sorter did nothing' with an empty log.
- The installed eksolutions.chestbutler.cfg is a stale 1.1.x file: it still has [Organize] MovesPerTick = 4 (a key that no longer exists — W1 replaced it with MovesPerSecond) and has no [Gather] and no [Gamepad] section. BepInEx preserves unrecognised keys as orphans, so reading MovesPerTick out of the file proves nothing. Rename it and let 2.0 regenerate it.
- [Gamepad] Enabled is bound LAZILY, on first access inside GamepadNav.Enabled — not in Plugin.Awake. The section therefore does not exist in the config file until a chest has been opened (or a crafting recipe selected) at least once in that session. Do not conclude the feature is missing because the section is absent at first launch.
- Turning [Gamepad] Enabled off at runtime does not undo anything. LinkRow/LinkVertical/AttachRowToAnchor simply return early; navigation already written to the vanilla Take All and Craft buttons — including the Navigation.Mode.Explicit flip — stays until the game is restarted. Always toggle this config with the game closed, and always restart before judging the result.
- The version string still reads 1.1.2 everywhere: the startup line is 'ChestButler 1.1.2 loaded' and the config header says 'created by plugin ChestButler v1.1.2'. That is correct for the dev branch (release-prep was deliberately skipped) and is NOT evidence that an old DLL loaded. Verify by file size 84,992 bytes / md5 60cca718058e7cad828c033b3b0591e2, or by the presence of the '[sorterchest] registered …' line, which only 2.0 emits.
- The sorter tick will not move anything while the chest UI is open (SorterBehaviour checks _container.IsInUse()), and it only runs on the ZDO owner with Player.m_localPlayer non-null. Close the chest and stay nearby.
- A newly created or newly relabelled home does not take effect instantly. SorterBehaviour caches a per-item-type 'no home' answer for MissCooldown = 10 s (stretched up to 6× by Throttle when the mod is over its cost budget), and that cache is NOT cleared by a sign edit — only the filter spec cache is. 'Late by up to ~10 s' is correct behaviour; 'never' is a bug.
- Signs bind to exactly one chest: within 2.5 m AND the chest must be the nearest tracked container to the sign (Filters.IsNearestContainerTo). In a tightly packed chest wall a sign can silently label the wrong neighbour. Keep chests ≥3 m apart during testing and put each sign hard against its own chest.
- The line must literally start with 'sort:' after trimming (case-insensitive). Tokens are comma-separated and lowercased; 'off'/'ignore'/'none' excludes the chest, 'p<number>' sets priority, a name matching an [ItemGroups] key is a group, anything else is an item token with optional '*' wildcards. A line like 'chest sort: ores' is ignored entirely.

## C6 — Gather's per-frame base scan — the mod's only completely unthrottled hot path

**Why:** Uncovered by every plan. GatherPatch.SetupRequirementListPrefix nulls `_sources`, and the postfix rebuilds it via `Gatherer.Sources()` — a full `ContainerTracker.AccessibleNear(player.pos, [Sorting] Radius = 128)` scan that per chest does a Vector3.Distance, a ZNetView validity check, `SorterZdo.PlayerCanAccess` (a reflected Container.CheckAccess delegate), `PrivateArea.CheckAccess`, a `Filters.GetSpec` (30 s cache, but a MISS re-parses every registered Sign and runs a full container scan per in-range sign), and then `Inventory.CountItems` ONCE PER INGREDIENT PER CHEST. Vanilla InventoryGui.Update calls UpdateRecipe every frame, so all of that runs at framerate for as long as the crafting panel is open. Critically, none of it is inside a `Throttle.Measure()` block — Throttle only wraps Organizer's plan/run and SorterBehaviour's tick — so the mod's own self-throttle is blind to it and can never back it off. On a 100+ chest hall with a 4-ingredient recipe that is ~400 CountItems plus ~100 access checks every frame.

**Setup**

- Do this on the biggest base you actually own, loaded — this is the same run that captures roadmap §9 item 8, so combine it with the BuildPlan measurement.
- If you have no big base: place 30 chests in a ring around a Workbench, all within 128 m, each holding a few stacks (`spawn Wood 50` etc. — contents matter less than chest count).
- Bring up the vanilla frame counter (`fps` in the console) or watch the frame-time graph in your usual overlay.
- Have a 4-ingredient recipe available at the station.

**Steps**

- Stand at the Workbench with the inventory CLOSED and note the steady-state FPS.
- Open the inventory on the Inventory tab and note the FPS.
- Switch to the Craft tab and select the 4-ingredient recipe. Note the FPS and leave the panel open for 30 s.
- Scroll rapidly through the whole recipe list for 10 s and watch for hitching.
- Quit, set `[Gather] ShowStorageCounts = false` in eksolutions.chestbutler.cfg, restart, and repeat steps 1-3.
- Quit, set `[Gather] Enabled = false`, restart, and repeat steps 1-3 as the true baseline.
- In the same session, open a sorter chest and press Organize once to capture the largest `[organize] BuildPlan took N.N ms` figure alongside the chest count in range.

**Expected**

- A measurable FPS drop between step 2 (Inventory tab) and step 3 (Craft tab with a recipe selected) IS the cost of Gather's per-frame scan. Record the delta and the chest count — that pair is the actual finding.
- `ShowStorageCounts = false` should NOT recover the cost: CountsShown only gates the Annotate call; `Gatherer.Sources()` and `CountInStorage` still run because the button label needs the totals. If turning it off DOES recover the cost, the code path is different from what it reads like and that is worth knowing.
- `Enabled = false` hides the button but note that RefreshButton's early-out happens AFTER the postfix has already done the scan — Gather.IsEnabled is checked in RefreshButton and OnGatherClick, not in SetupRequirementPostfix. So the scan may still run with the feature disabled. Confirm which.
- Record the `BuildPlan took N.N ms` value with the chest count — that is roadmap §9 item 8 and the one number the offline suite cannot produce.
- No `[throttle] ChestButler is using ...` line is expected here even if Gather is expensive, because Gather is not measured. That absence is itself the finding.

**If it fails:** A double-digit FPS drop just from selecting a recipe = the scan needs a cache (one Sources() per N frames or per recipe-selection change rather than per requirement-list rebuild) and/or a Throttle.Measure() wrapper so the self-throttle can see it. The scan still running with `[Gather] Enabled = false` is a straightforward early-out fix in SetupRequirementPostfix.

**Log lines**

```
[organize] BuildPlan took
[throttle] ChestButler is using
[gather] pulled
```

## C7 — The loop a real player lives in: Gather drains a chest Organize claimed, then Organize runs again

**Why:** No plan tests the two features against each other in the direction the player actually uses them. Gatherer.Sources() honours only `spec.Ignore` — it does NOT skip a chest carrying a `psort_home` marker, does not skip Manual chests (deliberate), and does not skip Sorter chests (AccessibleNear defaults excludeSorters: false). So Gather routinely half-empties exactly the chests Organize claimed. The open questions are whether the marker survives being drained, whether Organize then refills that chest rather than re-homing the bucket somewhere else, and whether a chest Gather empties COMPLETELY becomes a candidate for a different bucket to steal — OrganizePlanner.PickFreeChest prefers `empty` chests first and only refuses a chest via AnchorsAnotherLiveBucket if the bucket is still LIVE (i.e. still has items in the census). Drain the last of a type out of the base and its bucket goes dead, its marker is cleared by EmitHomeMarks, and the chest is up for grabs. That churn is invisible in the offline suite.

**Setup**

- A settled base: press Organize until it says `Nothing to organize`.
- Write down which chest holds wood and how much, which holds metals, and which holds the leather/hides. Confirm each shows a `Clear` button in its toolbar (on a non-sorter chest whose second button reads `Pin`, a visible `Clear` is the only observable proof that psort_home is set).
- A Workbench in range.
- Make one bucket small enough to exhaust: leave exactly 10 LeatherScraps in the hides chest and nothing else of that type anywhere in the base.

**Steps**

- At the Workbench select a recipe needing Wood and Leather scraps. Note the `(N)` annotations.
- Click Gather until the leather chest is COMPLETELY empty and a good chunk of wood has moved into your inventory.
- Re-open the (now empty) former hides chest. Does it still show `Clear`?
- Open the wood chest — partially drained but not empty. Does it still show `Clear`?
- Press Organize from the sorter chest and read the preview. Confirm.
- Grep for `[organize] home markers:`.
- Re-open both chests and see whether the wood came back to the same chest and whether the emptied chest was re-purposed for something else.
- Drop the gathered wood back into the sorter chest and press Organize once more.

**Expected**

- Step 3: the emptied chest still shows `Clear` — the psort_home ZDO string is not cleared by items leaving.
- Step 5/6: because `hides` now has ZERO items in the census, it is not a live bucket; EmitHomeMarks should emit a CLEAR for that chest, so expect `[organize] home markers: N claimed, 1 released` (or more). After that press, the emptied chest should show NO `Clear`.
- The wood chest keeps its marker and the wood you put back returns to THE SAME CHEST — not to a newly claimed one. That is the fixed point doing its job under the gather/craft/organize loop, which is the only loop that matters day to day.
- The emptied-and-released chest is now a legitimate free chest and may be claimed by whichever bucket is largest. That is correct behaviour, but confirm it does not cause a cascade: press Organize a third time and it must report `Nothing to organize`.
- Step 8: `Nothing to organize` on the press after the wood settles. If it takes two extra presses, the loop does not converge and the fixed point is only stable when nothing external touches the chests.

**If it fails:** Wood returning to a DIFFERENT chest than it came from = the psort_home fixed point does not survive a partial drain, and every craft session re-shuffles the base. `home markers: 0 claimed, 0 released` when a bucket has gone extinct = dead markers accumulate and those chests are permanently removed from the free pool (the §16.4.6 failure, seen from the marker side). More than one extra press to re-converge = the emptied-chest re-purposing is cascading.

**Log lines**

```
[organize] home markers:
[organize] BuildPlan took
[gather] pulled
0 move(s)
```
