01The vision

One or more chests are designated as Sorters. Anything dumped into a Sorter is automatically routed out to the right storage chest around the base. The player's entire interaction is: open sorter → dump everything → walk away.

User stories

As a player…The mod does…
I dump 3 stacks of stone into the sorterStone moves to the chest designated (or already holding) stone
I dump carrots, turnips, onionsAll route to the chest tagged with the Cooking group
I dump something no chest wantsIt stays in the sorter - never dropped, never deleted
My friend dumps loot at the same timeTransfers are RPC-routed to each chest's owner - no dupes, no loss
The target chest is fullRouter tries the next matching chest; otherwise item waits in sorter
A chest is behind someone else's wardRespected - the router never bypasses CheckAccess

Non-goals (v1)

No cross-base logistics (sorting only runs while the area is loaded, i.e. a player is nearby - Valheim unloads empty zones), no crafting-station auto-feed, no console/crossplay support (BepInEx is Steam-only), no item teleportation across the map. Phase 5 lists stretch goals.

03Code autopsy - why Smarter Containers deletes items

We read the full decompiled source (v1.7.0, via Thunderstore's decompiler). The mod is a single Harmony postfix on Inventory.AddItem: when you Ctrl-click an item into an open chest, it intercepts the add and re-routes the stack to a nearby chest. The fatal part is how it moves the item:

// Postfix on Inventory.AddItem - __instance is the OPEN chest's inventory
if (!__result) {                          // open chest was full…
    if (TryAddToNearBy(item)) { __result = true; }   // …lie to the vanilla caller
} else if (__instance.CountItems(item.m_shared.m_name) == item.m_stack
           && TryAddToNearBy(item)) {
    __instance.RemoveItem(item);
}

private static bool AddItemToContainer(ItemData item, Container target) {
    bool ok = target.GetInventory().AddItem(item);  // direct write, same object ref
    if (ok) { target.Save(); target.GetInventory().Changed(); }
    return ok;
}
Trimmed decompiled source, SmartContainers.dll v1.7.0 - the entire "transfer engine"

Grep of the full assembly confirms: zero occurrences of IsOwner, ClaimOwnership, or SetOwner. It writes directly into chests it doesn't own.

FLAW #1 - Writes to replicas

Valheim chests are owner-authoritative. A non-owner's local Inventory is a read-only replica; writing to it changes nothing real. The write silently evaporates on the owner's next ZDO revision - but the removal from your side (player inventory / opened chest) IS authoritative. Item gone. The Feb-2023 network rewrite made revision semantics strict, turning "rare loss" into routine loss on dedicated servers.

never touch a non-owned inventory; route every move through the owner (MultiUserChest RPC).

FLAW #2 - Forged success, no rollback

Setting __result = true tells vanilla code "the add worked", so vanilla unconditionally deletes the item from the source. When the remote add later proves phantom, there is nothing to roll back to.

no Harmony result-forging at all - we don't patch the insert path; we pull from a chest we own on a tick, transactionally.

FLAW #3 - Aliased ItemData object

The same object instance is inserted into the target while still referenced by the source; vanilla mutates m_stack during stack-merges. Against a stale replica this corrupts counts with no recovery.

full serialize-clone per move (MUC's WriteItemToPackage carries stack, quality, durability, customData - EpicLoot-safe).

FLAW #4 - "InUse" filter isn't safety

Its only concurrency guard skips chests currently open in someone's UI. A closed chest owned by another peer passes the check and still gets a phantom write. Candidates aren't even distance-sorted (registration order).

ownership-correct writes make concurrency safe by construction; candidates sorted by priority, then distance; wards (CheckAccess) respected.
What we keep from it
The UX ideas are good and battle-tested: chest-GUI buttons cloned from m_takeAllButton, item-name normalization ($item_ strip + lowercase), group model (system groups like ore, vegetables, wood + user-defined groups), HUD "Routed to another chest" feedback, and a 14 m default range. We rebuild the engine, keep the ergonomics.

04Proven building blocks (MIT, free to reuse)

Every risky mechanism our mod needs already ships in MSchmoecker's MultiUserChest (MUC) and ItemHopper - both MIT-licensed, actively maintained, and designed to be depended on (MUC changelog: "synced non-player interactions on chests… the base for other mods").

A. Safe cross-chest moves - MUC's extension API

// MultiUserChest/ContainerHandler.cs - public API we call for every move
public static RequestChestAdd AddItemToChest(this Container container, ItemData item,
    Inventory sourceInventory, Vector2i to, ZDOID sender, int dragAmount = -1)

// inside: source slot is blocked + item optimistically removed, then…
if (container.m_nview.IsOwner()) {
    response = container.GetInventory().RequestItemAdd(request);   // local, authoritative
} else {
    GamePatches.InvokeRPC(container.m_nview, ItemAddRPC, request); // routed to ZDO owner
}
// owner executes, responds; rejected leftovers are re-added or dropped - never vanish
Transactional by design: block slot → request → owner executes → response heals the source. Undeliverable items drop to the ground rather than disappear.

B. The tick loop - ItemHopper's owner-gated, staggered FixedUpdate

// ValheimHopper/Logic/Hopper.cs
private void FixedUpdate() {
    if (!IsValid() || !zNetView.IsOwner()) return;   // only the ZDO owner simulates
    // frameOffset = InstanceID % transferFrame  → hoppers stagger across frames
    if ((frame + frameOffset) % transferFrame == 0) { PullItems(); /* or */ PushItems(); }
    if ((frame + frameOffset + 1) % objectSearchFrame == 0) FindIO();  // re-scan every 3 s
}

C. Per-chest settings that save with the world - ZProperty pattern

// ValheimHopper/Logic/ZProperty.cs - ZDO-backed property with owner-write RPC
public void Set(T value) {
    if (NetView.IsValid() && NetView.IsOwner()) SetValue(value);   // direct ZDO write
    else NetView.InvokeRPC(RPCName, value);                        // ask the owner to write
}
// ItemHopper filters: one int per slot, key "hopper_filter_{x}_{y}",
// value = prefab name stable hash (0 = unfiltered) → syncs & persists for free

D. Discovery, versioning, stacking

  • Finding chests: Physics.OverlapBoxNonAlloc on the piece layers, dedup by ZDOID, cached 3 s. We swap in OverlapSphereNonAlloc(pos, radius) for a radius around the sorter.
  • Version lock-step: Jötunn's [NetworkCompatibility(EveryoneMustHaveMod, VersionStrictness.Minor)] - mismatched clients can't connect. This is how we guarantee server + all clients run the same version.
  • Stack edge cases: MUC's CanStack (name + quality when upgradable), ClampStackSize via prefab cache (safe with stack-size mods), full m_customData serialization (EpicLoot-compatible).
  • Opt-out flag: MUC honors a MUC_Ignore ZDO bool on containers - we set it appropriately and respect it in discovery.
Build vs. borrow decision
We take a hard dependency on MultiUserChest (as ItemHopper does) instead of re-implementing RPC transfer plumbing - that's the single highest-risk subsystem, already solved, maintained, and MIT. Our code stays focused on what's new: sorter designation, routing rules, filters, and UI. Bonus: MUC also lets multiple players open the same chest, which your camp will love anyway.

06The routing algorithm

Deterministic, explainable, loss-proof. Every stack in a sorter goes through this decision each cycle:

Fig. 2 - Per-stack routing decision. Green path = happy path; the red terminal is the ONLY failure mode: the item just sits in the sorter.

Tie-breaking & ordering rules

  • Specificity wins: a chest that names the exact item beats a group chest, which beats a contains-match. Your "Stone" chest outranks a "Building materials" chest for stone.
  • Priority number: each target chest has a user-settable priority (default 0); higher wins within the same specificity tier - lets you make an overflow chest that only fills when the main one is full.
  • Distance last: equal specificity + priority → nearest chest wins (Smarter Containers used registration order - a subtle bug we fix).
  • Stack-splitting: if the best target has partial room, we fill it and route the remainder to the next candidate (MUC clamps stacks safely).
  • Sorter chaining is prevented: sorters are never targets, so no infinite loops between two sorters.

09Player-facing design

On any chest GUI - one new button
┌ Reinforced chest ─────────────┐
│ [Take All] [⇄ Sorter: ON] │
│ …inventory grid… │
└───────────────────────────────┘

Toggle any chest into a Sorter. Its contents start draining to filtered chests immediately. Cloned from m_takeAllButton - the exact technique SC used, so we know it survives GUI updates.

On target chests - filter controls
┌ Filters ──────────────────────┐
│ groups: [cooking ✓] [seeds ✓] │
│ items: [Stone ×] [Flint ×] │
│ [📌 Pin current contents] ⬆0 │
└───────────────────────────────┘

“Pin current contents” is the killer shortcut: put a sample of what belongs in the chest, click once - every item type inside becomes an explicit filter. Zero menu digging for the common case.

Day-one usability without opening a single menu: thanks to the contains-fallback, an unconfigured base already routes items to chests that hold them - Smarter Containers behavior, minus the item loss. Filters and groups refine from there.

11Risks & mitigations

RiskLikelihoodImpactMitigation
Valheim 1.0 “Deep North” lands Sept 9, 2026 with an engine/networking pass - historical precedent says mods break HIGHHIGH Build now, enjoy the summer; budget a patch sprint mid-September. Pin the server via AMP's default_old branch until BepInEx/Jötunn/MUC update (they historically follow within days–weeks). Our thin-patch design (almost no Harmony patches on game internals) minimizes surface area.
MUC dependency goes unmaintained LOWHIGH MIT license - we can vendor/fork the ~4 files we use. Actively maintained today.
Ownership races / duplication bugs MEDHIGH All mutations owner-routed via MUC (its whole raison d'être); slot blocking + response self-heal; P4 dupe-hunt matrix is a release gate.
Performance on mega-bases (200+ chests) MEDMED 3 s discovery cache, staggered ticks, stacks/tick budget, full-chest cooldown, non-alloc physics queries. Only sorters tick - normal chests cost zero.
Conflicts with other inventory mods MEDLOW We patch no vanilla insert path (SC's postfix on Inventory.AddItem was its conflict magnet). BepInIncompatibility declared against known auto-sorters; respect MUC_Ignore.
Sorting pauses when no player is near the base CERTAINLOW Engine-level (Valheim unloads empty zones). Matches the use case - you dump loot while standing there. Documented for players.

12Deployment on your AMP server

AMP's Valheim template has native BepInEx support - no manual Doorstop wrangling.

StepAction
1AMP instance → Configuration → search “BepInEx” → enable Install BepInEx → run Update. AMP downloads denikson's BepInExPack and sets all Doorstop env vars itself. (Don't combine with the “Install Valheim Plus” option.)
2Disable crossplay (uncheck Enable Crossplay → Steam networking). Required for modded play; Xbox/Game Pass players can't join modded servers regardless.
3Upload DLLs via AMP File Manager to Valheim/896660/BepInEx/plugins/: Jotunn.dll, MultiUserChest.dll, ProjectSorter.dll.
4Start server → verify BepInEx/LogOutput.log shows all three plugins loading; tune generated configs in BepInEx/config/ (server values win - synced to clients).
5Players: one-click install via a shared r2modman/Thunderstore modpack code (pins exact versions). Anyone missing it or version-mismatched is refused at connect - by design.
6Update hygiene: leave Install BepInEx on (it re-applies each update; plugins/ and config/ survive). Add a backup trigger before updates. If a game patch breaks mods: switch Server Branch to default_old until the mod stack catches up.
